### Slide 2: 这个项目在做什么

# 让 AI 在信息不对称的博弈环境中打牌并自我进化

听起来不复杂，但实际做下来有两个工程问题比较棘手：

| | 问题 | 为什么难 |
|---|---|---|
| **环境可信** | 每个 Agent 只能看到它该看的信息 | 共享进程、共享事件存储都可能是泄露源；这类 bug 不容易发现 |
| **信号提取** | 从单局胜负中提取有效的进化信号 | 一局胜负随机性极大，直接用胜负驱动策略修改会震荡 |

→ 两个问题不是独立的：环境不可信，进化信号就是垃圾；信号提取不好，进化就是随机游走。

### Slide 3: 架构总览

# 双服务解耦：信息隔离 + 独立迭代

```
┌──────────────────────────┐           ┌──────────────────────────┐
│     编排层                │           │          Agent 层        │
│                          │  WS/HTTP  │                          │
│ 游戏引擎 · 声明式状态机    │ ◄───────► │ Reflect + Act 决策流      │
│ 视角隔离 · 玩家抽象        │           │ 四层记忆 · 进化管线        │
│ 匹配 · 观战 · 回放        │           │ GEPA · 共轭 Agent         │
└──────────────────────────┘           └──────────────────────────┘
```

解耦带来两件事：
- **信息物理隔离**：Agent 之间无共享内存/数据库/通信通道，编排层按阶段配置定向推送事件
- **部署独立性**：编排层改样式、加模块，Agent 无需感知；Agent 换 LLM、调策略，编排层不用改

# 把狼人杀从"人玩的游戏"变成"AI 可信博弈的环境"

### Slide 5: 声明式状态机

# 32 个游戏阶段，阶段转移抽象为纯函数

**问题**：7 种角色、32 个阶段、平票 PK、开枪链递归、同守同救悖论。用 if-else 写转移，阶段数超过 20 就难维护。

**做法**：

```python
# 传统：if-else 硬编码
if phase == NIGHT_BEGIN:
    if guard_alive: next = GUARD_ACTION
    elif seer_alive: next = SEER_CHECK
    ...

# 我们：数据驱动
PHASE_TRANSITIONS = {
    GamePhase.NIGHT_BEGIN: lambda s: GamePhase.GUARD_ACTION_BEGIN,
    GamePhase.WOLF_KILL:   lambda s: GamePhase.SEER_CHECK_BEGIN,
}

PHASE_SKIP_CONDITIONS = {
    GamePhase.GUARD_ACTION: lambda s: not s.is_role_alive(Role.GUARD),
}
```

| 对比 | 传统 | 我们 |
|------|------|------|
| 新增阶段 | 改 N 处 if-else | 加 1 行映射 |
| 角色死亡 | 每个处理器检查 | 自动递归跳过 |
| 条件分支 | 嵌套 if | `Callable[[State], Phase]` |

状态机核心逻辑约 30 行，改阶段流程动配置不动引擎。

9 处条件转移点覆盖平票 PK、开枪链递归、遗言后分支等。

**局限**：漏定义的转移路径不报错而是静默失败，目前靠测试覆盖，没有自动化完整性校验。

### Slide 6: 视角隔离

# 信息不对称是游戏基础

**问题**：广播所有事件，对局直接作废；手动控制推送范围，容易遗漏且难审计。共享进程/内存本身就是泄露源——代码层面的权限控制挡不住侧信道。

**方案**：

**物理隔离** — 编排层与 Agent 层独立部署，每个 Agent 为独立进程，无共享内存/数据库/通信通道。

**声明式可见性** — 引擎为每个阶段声明事件的可见范围：32 个阶段中 6 个私密 + 2 个半私密，其余全局广播。

**一套声明，三个场景**：
- 对 Agent：确保信息隔离
- 对观战者：清晰展示每个对象的可见范围
- 对人机对战：可直接复用为人类玩家的视角隔离

**代价**：12 人局起 12 个独立进程，资源占用不低。可见性声明为静态配置，不支持运行时动态调整。

### Slide 7: 玩家抽象与通信协议

# 三种接入方式，ACT/PERCEIVE 二元协议

**玩家抽象**：抽象基类隔离引擎与玩家实现，引擎只操作接口列表，新增类型无需改动引擎。

| 接入方式 | 特点 |
|---------|------|
| HTTP | 编排层作为客户端主动调用 Agent 暴露的端点 |
| WebSocket 长连接 | 支持自动重连、思考过程回调 |
| 人类玩家 | WebSocket，支持断连重连与行动超时 |

**ACT/PERCEIVE 二元协议**：

```
init / init_ok        握手，分配角色
perceive              感知推送（fire-and-forget）
act / act_result      行动请求-响应（带超时）
thought               Agent 主动思考广播
```

协议将 19 种游戏阶段归一化为动作类型，34 种事件类型归一化为感知类型。事件记录经五步流水线完成：推导可见性 → 日志记录 → 对象构建 → 实时推送 → 落库。

**关键设计**：游戏服务器主动连接 Agent 服务（降低接入门槛），自然语言意图解析（`"我要上警"` → 上警意图识别）。

### Slide 8: 对局管理与匹配

# 5 种匹配模式，camp_evolution 是进化实验的关键桥梁

- **板子**：12 人标准局，死亡结算区分击杀、毒杀、悖论三种死因

| 模式 | 用途 |
|------|------|
| 随机抽人 | 基线 |
| 跨版本对抗 | A/B 对比 |
| Elo 梯度 | 同水平 |

### Slide 9: Agent 层总览

# 从高噪声对局中提取进化信号

Agent 层的核心贡献：一条进化管线，把原始对局结果转化为可信的策略变更。

**决策流**：

```
         ┌──────────┐
    ───► │ PERCEIVE │ ────┐
         └──────────┘     │
                    ┌─────▼─────┐
                    │  REFLECT  │   ← 1 次 LLM 调用：分析局势、提取矛盾
                    └─────┬─────┘
                          │
                    ┌─────▼─────┐
                    │    ACT    │   ← 1 次 LLM 调用：Function Calling（11 个工具）
                    └───────────┘ ────► 决策输出
```

**LLM 接入**：基于 OpenAI 兼容协议，当前使用 DeepSeek，可切换 Provider。

### Slide 11: 去抖 — 为什么不能一局一改

# 单局胜负是高噪声信号

```
直接用胜负驱动：输一局 → 立即改策略 → 震荡 → 再输 → 再改 → 再震荡
```

去抖管线把策略变更触发条件从"1 局"提升到"至少 2-3 局一致建议"：

- **缓冲池**：积累原始建议，不立即生效
- **场景聚类**：合并相似建议（核心维度权重 0.75，次要维度 0.25）
- **双阈值确认**：标准通道（一致率 ≥ 50% + 因果强度 ≥ 0.35）/ 快速通道（因果强度 ≥ 0.7）

**代价**：进化速度变慢，需要多局积累才能触发变更。这是为稳定性做的权衡。

### Slide 12: 因果强度分离 

# 高置信 ≠ 高因果：赢了可能是运气

**核心洞察**：直接把胜率当进化信号会引入伪进化。

**三路分离计量**：

```
因果链分析（LLM 判断策略与结果的因果强度）
× FLAG 加成（对局中实时标记 ×1.3）
× 匹配度折扣（场景不匹配 ×0.7）
= 最终进化建议强度
```

**FLAG 机制**：Agent 在反思时发现策略与局势矛盾，标记 `[FLAG]`，对局结束后纳入进化管线。有 FLAG 标记的建议因果强度 ×1.3。

**诚实交代**：因果链分析依赖 LLM 判断，而 LLM 对"因果"的理解并不总是可靠的。目前没有做过"使用因果加权 vs 不使用"的对比实验，因果加权到底带来了多大改善，还不确定。

### Slide 13: GEPA 帕累托优化

# 只看胜率 → 策略同质化，四维评估保留多样性

**问题**：单维度优化导致所有策略趋向保守求稳。

**做法**：四维适应度评估——胜率、一致性、欺骗性、信息利用。非支配排序保留 Pareto 前沿，保证每个维度最强的个体不被淘汰。

```
consistency
  1.0 ┤    ●
      │  ●   ●      ● = Pareto 前沿（各维度最强）
  0.6 ┤●   ○   ●    ○ = 被支配个体
      │  ○     ○
  0.0 ┼──────────── win_rate
```

| 机制 | 实现 |
|------|------|
| 变异 | LLM 诊断最弱维度，语义重写策略 |
| 交叉 | LLM 融合两个前沿个体的精华（同角色才交叉） |
| 采样 | 角色均衡——每角色至少 1 个代表，剩余按胜率轮询 |
| 冷启动保护 | 数据不足时胜率线性衰减，避免少样本高胜率的虚假优势 |

种群 8 个体 / 10 代。

**诚实交代**：GEPA 运行若干代后的 Pareto 前沿分布和胜率提升，还没有系统性的量化数据。

### Slide 14: 共轭 Agent

# 策略版本组合的快照，让进化对人类可见

当某个策略的默认版本变化时，新共轭体诞生：

```
策略 v1.2 ──晋升──► 新共轭体诞生
                    │
                    ├── 名字：影刃-初纪 → 霜牙-二纪 → 烬瞳-三纪 ...
                    ├── 指纹：{所有策略当前默认版本的 SHA256 哈希}
                    └── 人格：LLM 基于指纹生成个性化表达风格
```

- 旧人格可回溯、可对比、可回滚
- 为 camp_evolution 提供可冻结的历史版本

不是核心机制，是进化结果的可读化。

### Slide 16: 跨层闭环 

# camp_evolution × GEPA：环境控制与进化算法的协同

Agent 进化需要可控实验环境——相同阵营配置、相同对手，只变量是策略版本。传统匹配无法控制这些变量。

```
平台创建对局 ──► Agent 博弈 ──► 记录结果
     ▲                              │
     │                              ▼
     │                        Agent 反思
     │                              │
     │                              ▼
     │                        策略进化（去抖+GEPA）
     │                              │
     │                              ▼
     └──── 回放证据链 ◄──── 平台再次评测
```

编排层保证对比公平性（相同配置），Agent 层保证进化方向性（Pareto 优化），回放链保证结果可追溯性。

**当前状态**：camp_evolution 实验数据还比较有限，跨版本对抗的胜率变化需要更多对局积累。

### Slide 18: 做对了什么 / 还缺什么

# 诚实的复盘

**做对了的**：
- 物理隔离 + 声明式可见性，环境可信度有保障
- 去抖 + 因果分离，进化信号质量比直接用胜负好
- 双服务解耦，两层独立迭代
- 声明式状态机，改阶段流程动配置不动引擎

**还不够的**：
- 去抖实际过滤比例、因果加权 vs 不加权的对比——缺量化验证
- GEPA 运行代数有限，Pareto 前沿的收敛行为还没有系统观察
- camp_evolution 实验数据不足
- 状态机转移完整性没有自动化校验
- 12 个独立进程的资源开销
